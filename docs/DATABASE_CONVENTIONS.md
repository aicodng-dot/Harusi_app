## TARGET — mandatory conventions for future changes

- Preserve existing primary keys, QR tokens, guest manual codes and admission history. Do not convert all IDs to UUIDs or reinterpret existing offline external identifiers.
- Keep names compatible with existing code; use plural snake_case for new tables and `<entity>_id` relationship columns. Add explicit foreign keys, unique constraints and indexes only after data validation and query needs justify them.
- Make every customer resource traceable to workspace/event. Validate parent-child consistency atomically; choose composite constraints or equivalent guarded write paths after reviewing actual schema. Never rely only on client/session IDs.
- Keep canonical phone values as strings in `+255…` format. Inspect/deduplicate account phones before introducing uniqueness; guest phones are not account identifiers and need not be unique.
- Preserve leading zeros in manual codes. Their four-digit namespace allows at most **10,000** distinct codes per event (`0000`–`9999`); [ManualCodeService](../app/Services/ManualCodeService.php) checks exhaustion. No silent code regeneration or capacity expansion.
- Keep UTC for instants and explicitly define presentation/event timezone. Do not shift date-only event dates. Use exact decimal or integer minor units with explicit currency for future money; no floating point. Billing fields are not implemented.
- Admission changes must use a transaction and appropriate row locks around authoritative counts. Enforce `0 ≤ used_entries ≤ allowed_entries ≤ 10`; do not rely on unsigned column types or UI checks for the whole invariant.
- Define deletion/retention per relationship before changing cascades or adding soft deletes. Preserve auditable admission history, offline provenance and reconciliation records; data retention periods require approval.

## PLANNED — additive migration and verification rules

Before any data migration, take a protected database/file backup and verify restore on an isolated copy. Capture migration history, schema, counts, orphan/duplicate checks and immutable identifiers. Rehearse on the actual supported database engine and a representative legacy copy. A migration file existing is not evidence it ran.

For tenancy: add workspaces/memberships and nullable event ownership; review Legacy Workspace ownership mapping; backfill idempotently in bounded batches; verify every event and downstream relationship; only then tighten nullability/foreign keys. Keep old scanner assignments until replacement assignments and offline references reconcile. Never run `migrate:fresh`, broad rollback, seeders or recovery scripts against production as a routine deployment step.

Document forward repair and restore procedures separately: reversing DDL cannot recover deleted data. Verify migration locks/duration, engine-specific DDL behavior, generated columns, index names and restore consistency before a maintenance window. Do not add indexes blindly.
