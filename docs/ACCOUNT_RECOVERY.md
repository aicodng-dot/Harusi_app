## IMPLEMENTED — P2-003 registered-email recovery

[PasswordRecoveryController](../app/Http/Controllers/PasswordRecoveryController.php) exposes GET/POST /forgot-password, GET /reset-password/{token} and POST /reset-password through web sessions and CSRF. Email or canonical Tanzanian phone resolves through LoginIdentifier; only the matched active admin/scanner/customer account's registered email receives a reset link. Explicit identifier takes precedence over legacy email input. Known, unknown, malformed and unavailable accounts receive the same response, without disclosing account details or the destination email.

[SendPasswordResetLink](../app/Jobs/SendPasswordResetLink.php) runs through the same single-use Laravel deferred callback after every accepted request, including unknown inputs. It is not a persistent queued job and needs no permanent worker. The existing users broker retains hashed token storage, 60-minute expiry, 60-second issuance throttle and its minimum timebox. Recovery and reset each have independent 10/minute IP and normalized-identifier limits; reset uses the actual submitted email. No SMS or WhatsApp OTP is sent.

Reset links use trusted APP_URL rather than the incoming Host. Forms escape values and use no-store and no-referrer headers. Reset tokens/passwords are excluded from flashed validation input. A dedicated safe mail transport is required: log mail and composite failover/roundrobin transports are rejected, including URL driver overrides and nesting/cycles. Delivery failures record only a safe reason or exception class; exception messages, reset URLs and recipients are not logged by the delivery class.

## IMPLEMENTED — password and session revocation

The reset transaction locks user/token rows, validates the broker token, explicitly hashes the chosen password, rotates remember_token and consumes the token. A failure rolls back credentials and token changes; success never automatically logs the browser in. Expired, invalid, replayed or unavailable-account reset attempts fail generically.

Successful login seeds a password HMAC in the browser session. AuthenticateWebSession checks it after EnsureActiveAccount refreshes persisted identity; a changed password invalidates older sessions on their next request. Genuine persisted legacy sessions without a marker require one-time reauthentication. Valid remember-cookie restoration creates a new marker; old remember credentials cannot restore access after reset. This also covers password changes made through existing administrative account management.

P2-004 now deletes all account API tokens inside the reset transaction; failure rolls back both credentials and revocation. Administrative password edits use the same user-row transaction boundary and revoke tokens too. Downloaded offline authorization cannot be remotely invalidated while disconnected. Historical pending result imports remain recoverable.

## IMPLEMENTED — P3-018 selected MySQL evidence (2026-10-21)

All **four selected actual MySQL 8.4.11 cases / eight independent PHP HTTP-kernel workers** passed across four fresh synthetic schemas (27 repository migrations / 31 tables each). Three pairs observed actual owned-thread users RECORD lock waits and complete precommit row invisibility. Reset/reset ended at 302 success / 422 generic replay refusal; reset-before-old-password login ended at 302 / 401; old-password login-before-reset ended at 201 / 302, with its newly issued token then removed by the reset. Accepted calls executed exactly three DML statements; refused contenders executed zero.

Each completed reset replaced only the target account password/remember token/updated_at, accepted the new password and rejected the old, consumed the target reset row and removed all target device tokens. The unrelated account, its reset/device rows and every other row across all 31 tables matched the baseline exactly, including guest manual code, QR token, counters and history. SHOW CREATE definitions matched with allocator counter values excluded; no AUTO_INCREMENT restoration is claimed.

Terminating only the identity-verified owned reset worker after its completed uncommitted password/remember UPDATE and before token deletion caused complete database row rollback. Its MySQL thread disappeared and the full prior snapshot was restored, including password/remember/reset/device rows; the original reset token then succeeded on a fresh retry worker. Bounded polling accounted for rollback visibility after thread teardown.

These are selected synthetic transaction schedules on the recorded MySQL build, not exhaustive concurrency, power-loss durability or another hosting environment. HTTP kernel calls used APP_ENV=testing (CSRF bypass) and array sessions/cache, so deployed browser/session/rate-limit behavior and SMTP/device delivery remain unverified. PasswordReset events dispatch synchronously inside the transaction: database rollback cannot undo arbitrary external listener effects; no such app listener was found and no external-effect guarantee is claimed. A token issued by an earlier valid login can subsequently be revoked; already-running requests are not retroactively cancelled. No configured/customer database, XAMPP/other service, account/ownership/grant, API/UI/Android/dependency change or deployment occurred. Real ownership/platform approval, customer database/private-file restoration and maintenance fencing remain open; Phase 3 remains IN PROGRESS. [Guide](MYSQL_RECOVERY_REHEARSAL.md).

## IMPLEMENTED — P4-003 customer identity boundary (2026-10-22)

A distinct customer account can sign in by existing email/phone/password, remember its session, recover through its registered email and reach only its protected read-only workspace home. Raw customer identity IDs must be canonical positive integers within PHP range before Eloquent casting; new customer role never becomes admin/scanner/platform. Primary web account refresh precedes role checks. The independent EN/SW home selects only its own active owner/manager memberships, with fresh account predicates, real workspace parents, fixed 15-row pagination, escaped names and private no-store/no-referrer headers. It neither composes the admin layout nor queries events/guests/files. Legacy staff index and bound read/update/delete now exclude customer/unsupported identities, with fresh primary reads before validation and role predicates repeated on locked write targets. Legacy staff forms cannot create/promote a customer. New customer recovery eligibility is consistent in deferred send and reset; device token eligibility remains active admin/scanner only. Dormant authority/provisioning can accept active customer creators for new workspaces; legacy backfill eligibility is unchanged.
