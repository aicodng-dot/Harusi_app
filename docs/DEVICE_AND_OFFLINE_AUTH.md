# Device and offline authentication

Audit: 2026-10-11. See [authentication](AUTHENTICATION_ARCHITECTURE.md), [Android status](ANDROID_SCANNER.md), and [offline protocol](OFFLINE_SYNC.md).

## Current trust boundaries

**CURRENT:** Browser scanners use shared email-or-phone/password Laravel sessions and scanner role; event assignment is users.event_id. P2-002 refreshes persisted account/role, denies unavailable online identity and restricts new offline enrollment to active scanners. Offline administration requires admin/event policies. P2-004 adds the same-account HTTPS bearer login/me/logout foundation, while trusted physical-device enrollment, tenant/scanner APIs and Android implementation remain planned. [User](../app/Models/User.php), [routes](../routes/web.php), [offline policy](../app/Policies/OfflineScannerSessionPolicy.php), [admin checks](../app/Http/Controllers/Admin/Concerns/HandlesOfflineScannerAdmin.php).

Package generation includes event-authorized scanner users, assigned gates, master/client roles and permission strings. Session bootstrap, result encryption, result authentication and device pairing secrets are separate random 32-byte values; Laravel encrypts them at rest with `Crypt` and the models hide secret fields. The package password encrypts the entire exported payload. [Builder](../app/Services/OfflineScannerPackageBuilder.php), [session model](../app/Models/OfflineScannerSession.php), [crypto](../app/Services/OfflineScannerPackageCryptoService.php).

**IMPLEMENTED P2-002:** new package UI/request/builder reject inactive master/client accounts with a locked persisted check; tests passed in the265-test suite. Already downloaded packages cannot receive instant revocation while isolated. Current account suspension does not discard historical package/result admissions; historical import code remains unchanged.

**CURRENT SECURITY GAP:** `createSessionUser()` sets `offline_pin_verifier = PBKDF2-HMAC-SHA256(user_id + "|" + session_uuid, salt, 120000)`. Both identifiers and the salt are exported. No user-chosen or secret PIN is verified. Despite its name this value must not be described as secure offline PIN authentication. Fixing it needs a versioned client-compatible design and tests; no authentication changes were made in this audit.

**CURRENT:** Exported device permissions are declarations. Result validation requires exactly one master, known active session users, matching roles/gates, matching source device records, and bound event/session/package identifiers. The result file uses a shared session encryption key and AES-GCM authentication. Possession of that key is not independent proof of a unique physical master device. A separate `result_file_authentication_secret` exists in packages but the current result decryption contract does not use it. [Result validator](../app/Services/OfflineScannerResults/OfflineScannerResultsValidator.php), [result crypto](../app/Services/OfflineScannerResults/OfflineScannerResultsCryptoService.php).

## IMPLEMENTED — P2-004 online token lifecycle

Sanctum4.3.3 issues tokens only after locked shared-credential checks. Tokens are hash-only in storage, have auth:read/auth:logout abilities, expire after24hours without sliding or refresh, and are bounded to10 per account by oldest-token revocation on new login. Device name is metadata, not hardware identity. Browser cookies cannot authenticate the API; API logout revokes only the current token and does not alter browser sessions.

Protected API calls reload persisted active supported-role account state. Scanner login/me additionally require the persisted active event assignment; admins do not require an assigned event. Logout accepts a valid current token after assignment loss or event unavailability. No default-event fallback is used. Recovery and admin credential/availability/role/event/gate changes revoke tokens transactionally. Token expiry/logout never deletes downloaded packages or unsynced admission journals. Full isolated regression passed **353 tests / 3,049 assertions** (124.386315s), including **48 tests / 875 assertions** in DeviceTokenAuthenticationTest. New-file Pint, 15 PHP syntax checks and scoped whitespace checks passed. Runtime registers97routes: the prior94 plus the three versioned auth endpoints; no Sanctum CSRF-cookie route is enabled. Tests use SQLite memory, fake notifications/HTTP and temporary Laravel storage. Existing public/build, .env and unrelated checked source are preserved.

## Target lifecycle and unresolved decisions

**TARGET:** First online login verifies the ordinary Laravel account and event assignment. Store access credentials in Android protected storage; never store plaintext account passwords. A PIN/biometric unlocks only a previously authorized local session. Require HTTPS. Do not invent separate web/Android identity roles.

**PLANNED:** Before enabling mobile/offline authentication, verify the implemented online token policy on actual Android/hosting and specify physical-device enrollment/recovery, package trust-key distribution/rotation, local unlock retry limits, encrypted cache storage, offline authorization expiry and a trusted-time strategy. Online token lifetime is the P2-00424-hour contract; offline lifetime and hardware trust assumptions still require their own contracts.

| Situation | Target behavior / evidence gap |
|---|---|
| Network lost with valid cached authorization | Access only previously assigned cached event under the approved offline policy; Android enforcement unverified |
| Account/event permission revoked on server | Apply at next connection; immediate revocation cannot reach an isolated device; document maximum offline validity |
| Package expiry | Export contains `package_expires_at`; real Android enforcement unverified; expiry must not silently discard unsynced admissions |
| Logout, token expiry or app restart | Preserve encrypted unsynced admission journal; revoke/lock access separately from deleting event records |
| Device lost/replaced or master unavailable | Explicit recovery/export/reconciliation procedure; no automatic unsafe reset of counters |
| Upload from an unauthorized event/device | Reject and audit; do not trust submitted event/user/gate identifiers alone |

**REQUIRES VERIFICATION:** Device keystore use, biometric/PIN implementation, local database encryption, package password entry, pairing transport, revocation while offline, restart recovery and token expiry. The Laravel session package is evidence of server-side provisioning, not proof these client controls exist.

## IMPLEMENTED — P3-018 selected recovery/token MySQL checks (2026-10-21)

All **four selected actual MySQL 8.4.11 cases / eight independent PHP HTTP-kernel workers** passed across four fresh synthetic schemas (27 repository migrations / 31 tables each). Three pairs observed actual owned-thread users RECORD lock waits and complete precommit row invisibility. Reset/reset ended at 302 success / 422 generic replay refusal; reset-before-old-password login ended at 302 / 401; old-password login-before-reset ended at 201 / 302, with its newly issued token then removed by the reset. Accepted calls executed exactly three DML statements; refused contenders executed zero.

Each completed reset replaced only the target account password/remember token/updated_at, accepted the new password and rejected the old, consumed the target reset row and removed all target device tokens. The unrelated account, its reset/device rows and every other row across all 31 tables matched the baseline exactly, including guest manual code, QR token, counters and history. SHOW CREATE definitions matched with allocator counter values excluded; no AUTO_INCREMENT restoration is claimed.

These are selected synthetic transaction schedules on the recorded MySQL build, not exhaustive concurrency, power-loss durability or another hosting environment. HTTP kernel calls used APP_ENV=testing (CSRF bypass) and array sessions/cache, so deployed browser/session/rate-limit behavior and SMTP/device delivery remain unverified. PasswordReset events dispatch synchronously inside the transaction: database rollback cannot undo arbitrary external listener effects; no such app listener was found and no external-effect guarantee is claimed. A token issued by an earlier valid login can subsequently be revoked; already-running requests are not retroactively cancelled. No configured/customer database, XAMPP/other service, account/ownership/grant, API/UI/Android/dependency change or deployment occurred. Real ownership/platform approval, customer database/private-file restoration and maintenance fencing remain open; Phase 3 remains IN PROGRESS. [Guide](MYSQL_RECOVERY_REHEARSAL.md).

## IMPLEMENTED — P4-003 customer identity boundary (2026-10-22)

A distinct customer account can sign in by existing email/phone/password, remember its session, recover through its registered email and reach only its protected read-only workspace home. Raw customer identity IDs must be canonical positive integers within PHP range before Eloquent casting; new customer role never becomes admin/scanner/platform. Primary web account refresh precedes role checks. The independent EN/SW home selects only its own active owner/manager memberships, with fresh account predicates, real workspace parents, fixed 15-row pagination, escaped names and private no-store/no-referrer headers. It neither composes the admin layout nor queries events/guests/files. Legacy staff index and bound read/update/delete now exclude customer/unsupported identities, with fresh primary reads before validation and role predicates repeated on locked write targets. Legacy staff forms cannot create/promote a customer. New customer recovery eligibility is consistent in deferred send and reset; device token eligibility remains active admin/scanner only. Dormant authority/provisioning can accept active customer creators for new workspaces; legacy backfill eligibility is unchanged.

Full isolated regression passed **1,071 tests / 20,461 assertions** (170.769364s), with zero errors/failures/skips. Focused identity/home/auth/recovery/token/ownership regression passed **378 tests / 9,730 assertions** (55.085574s). The 60 new cases comprise 41 identity cases / 439 assertions and 19 home/admin-boundary cases / 286 assertions; both classes passed in the full run. Two cached raw-ID alias regressions first reproduced an incorrect HTTP 200 (expected 401), then passed with zero account lookups/writes and exact fixture/remember-token preservation after the raw-ID check was moved before the primary reread. Task PHP Pint/syntax, all 98 runtime route method/path pairs and the unchanged 32-table safe read-only CLI smoke passed.

This adds no signup, customer-account creation, workspace/event/guest/file writer, membership activation/grant or real-data migration. No configured account, ownership, password, token, environment/app key, service, dependency or existing build was changed. Existing legacy event/switcher/report/file/static-QR surfaces remain global and need isolation before customer event/writer exposure. Full customer portal/onboarding, complete action/resource policies, actual MySQL provisioning DDL/contention, actual database/private-file restore/legacy mapping/fencing, deployed SMTP/hosting and real browser/device/bilingual layout validation remain open. HTTP/HTML/DOM/source checks are not visual/device proof. Denied bearer requests may update only Sanctum's existing last_used_at/updated_at telemetry before middleware rejects; token identity/hash/abilities/expiry remain unchanged and no customer token is issued. Controlled target-role transition tests are fixture schedules, not concurrent-engine proof. Existing device middleware still uses default-read account refresh; primary-only web tests do not establish replica-safe bearer revocation. [Reference](CUSTOMER_WEB_IDENTITY.md).
