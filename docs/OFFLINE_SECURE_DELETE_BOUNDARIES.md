## IMPLEMENTED — three independent stages

P4-038 now protects legacy secure deletion as three separate exactly-one-attempt default-connection stages: bytes, metadata and audit. A reusable current-primary Event → exact active administrator → Session → Artifact guard retains SQL namespace predicates and raw identity/lineage/target checks. Captured scalar class/IDs and raw path/disk/fallback never come from callback-mutated models. Provider/direct branches remain exclusive; no outer transaction, repeated unlink, write fallback, ordinary parent reload or disk recalculation is added.

The authorized byte stage captures immutable scalar asset context, including raw nullable hash/size, Package UUID or Import UUID/results/source-package export identities. Metadata validates that asset and expected undeleted state, invokes the original update once and requires strict true. It repeats current authority/asset checks after callbacks, reads the actual primary persisted deletion timestamp/canonical deleter/exact reason and publishes the scalar receipt only after successful transaction return. Audit validates that asset and this marker, invokes the original audit once, repeats current authority/asset/marker checks and verifies the returned candidate's canonical insertion identity plus an actual primary locked row with exact FILE_DELETED action, Event/Session/actor/reason and complete existing metadata. Unsaved/cancelled creates, wrong database-only marker/payload and older matching rows cannot substitute for the completed write within the declared trusted callback flow.

Retention remains the entry/byte enable flag; disabling it after authorized bytes does not independently veto recording that phase. Protected stages retain ordinary/platform/member administrators, historical package/result eligibility, missing bytes and captured disks. No-provider helpers retain their trusted direct composition and SQL level0/PDO false. Existing metadata UPDATE and audit INSERT bodies are reused unchanged, and the final fresh() remains a separate read boundary.

### Preserved failure contract

These outcomes are verified by the existing [deletion feedback](../tests/Feature/OfflineScannerDeletionFeedbackTest.php) and [boolean/missing-file](../tests/Feature/OfflineScannerSecureDeletionResultTest.php) tests using invented data and fake storage.

| Outcome under normal HTTP autocommit | Current effect |
|---|---|
| Retention disabled | Refuse before bytes or metadata/audit writes |
| Missing path or file | Continue with existing metadata/audit behavior; absence is not physical erasure proof |
| Reported false deletion or storage exception | Refuse before metadata/audit; adapter byte effects may already be partial |
| Metadata UPDATE fails after unlink | Bytes are gone; metadata remains unchanged; no audit |
| Audit INSERT fails | Bytes are gone; metadata remains committed; no audit |
| Successful helper | Metadata/audit complete; a true unlink result does not establish forensic erasure |

An enclosing caller transaction can change SQL commit/rollback outcomes; unlink remains irreversible. A transaction around the whole helper or HTTP action would change the audit-failure row above. It cannot be called an authority-only change or make files transactional.

The existing17-case/353-assertion deletion-compatibility gate retains every prior test assertion and named outcome field. Provider success returns its current resource/Session/actor/path/disk only after the byte transaction completes. The helper then performs its unchanged metadata UPDATE and audit INSERT independently; there is no new enclosing HTTP/helper transaction. Provider error cannot enter the direct branch. A failure after unlink, including a byte transaction commit failure, receives no restoration guarantee.

## HISTORICAL — P4-037 reviewed design (2026-10-29)

The following planned language records the design before P4-038 implementation; it is retained as historical evidence.

### P4-037 reviewed design checkpoint (2026-10-29)

P4-037 is COMPLETE as a read-only design audit, with independent review required before completion documentation is applied. P4-036 remains the latest implemented source gate at **1,937 tests / 37,724 assertions** by356 exact source fingerprints; all366 non-doc baseline paths remain preserved. No new suite or fixture run is claimed.

This design adds no runtime metadata/audit guard. The next source task will add separate optional trusted metadata and audit providers after the existing byte provider. Each stage receives the current five-key context plus one write callback. Providers must propagate failure without falling back to an unguarded write. With no providers, direct trusted helpers retain their existing composition. No outer transaction or repeated byte operation is permitted.

The protected service must keep immutable operation-local scalar receipts, rather than later derive expectations from a mutable caller model. At the authorized byte point, capture raw class/PK/Session/Event, raw path/disk, resolved actual disk and the asset fields used by the deletion audit: Package UUID or Import UUID/results-export identity, raw hash and size. Source-package export identity for results is also part of the declared asset context. Nullable values remain nullable; do not invent a timestamp, hash or token. Unrelated archived/revoked/status fields do not become new retention prerequisites.

**Metadata stage:** start one new current-primary Event → active exact administrator → Session → Artifact transaction, with the same namespace SQL predicates and raw checks as the byte stage. Require matching asset context and expected undeleted state, then invoke the existing metadata update callback once on the current locked models. Require the actual metadata update boolean to be strict true and revalidate current authority plus the persisted row through primary locking reads using immutable captured class/Artifact/parent IDs and scalar expectations before commit; locks do not prevent this connection's own callbacks from changing authority or asset fields. The metadata callback must return the actual update boolean, not discard it through a void closure. A strict false/cancelled update or missing/unexpected persisted deletion marker must fail without invoking audit or claiming success. Publish the next-stage receipt/context only after the stage transaction returns successfully. The receipt contains actual persisted secure_deleted_at, canonical deleter ID, exact reason and declared asset context; do not guess timestamp precision from the application clock. Canonicalize IDs with the declared strict parser, retain the database timestamp representation read back from the row, preserve nullable hash/size and exact reason semantics, and reject unexpected persisted field types rather than silently coercing a marker. Publish it to the next stage only after this transaction returns successfully.

**Audit stage:** start its own one-attempt current-authority transaction and require the same asset and the marker written by this invocation's metadata stage. Do not require secure_deleted_at to be null. Invoke the existing audit callback once using current locked models. Verify through the primary connection that a newly persisted audit row has action exactly FILE_DELETED, expected Event/Session/actor/reason and full equality with the existing asset metadata built from immutable scalar expectations, including nullable/type semantics; an unsaved model returned after a cancelled create is insufficient. Revalidate authority/asset/marker after callback execution within this same transaction before commit. All post-callback lookups use immutable captured IDs and scalar expectations, never identity or asset fields read back from a callback's mutable model. The audit callback returns its newly created model for canonical candidate PK and actual primary persistence verification; exists/wasRecentlyCreated flags alone are insufficient. The implementation must distinguish the callback's newly inserted identity from an older matching historical row, with explicit positive/cancelled-create tests rather than assuming row existence proves a new insert. Publish successful next-stage context only after commit returns. No second byte access or metadata write belongs in this stage.

The global retention enable flag remains a byte-point rule. Disabling it after authorized bytes were removed must not independently prevent recording that completed phase. Namespace/actor/asset/marker authorization is still required at each later write. Normal HTTP autocommit continues to commit metadata before the audit stage, so audit INSERT refusal retains the metadata marker. New protected stage transactions also introduce callback/commit failure windows: metadata model-callback refusal can roll back its metadata write, and audit model-callback refusal can roll back its audit row. Name and test these outcomes; do not claim every legacy failure is unchanged. Bytes remain irreversible.

The receipt correlates this closed invocation with persisted state; it is not an unforgeable operation ledger. Identical same-precision arbitrary external rewrites, reference deletion/rebinding, trigger behavior and filesystem provenance are not solved by comparing a marker tuple. No schema/operation-token addition is authorized by this design. The final fresh() read remains a separately named read boundary.

Future source tests must cover late changes after byte return and after metadata commit, changed asset/marker fields, current Actor/Session/Artifact context, missing-file compatibility, disabled retention after bytes, cancelled writes, before-SQL and after-write callback faults, actual persisted receipts and no repeated unlink. Keep every existing deletion-failure partial-effect and private-feedback assertion. The existing HTTP feedback SQL-attempt observation must explicitly change from level0/PDO outside a transaction to level1/PDO inside the protected stage, while preserving request start/end autocommit0 and the class's case/assertion counts. Add separately named trusted direct-helper controls retaining the old level0 SQL observations; never bypass providers in an HTTP fixture to hide the new stages. Adapt the old byte fixture only to forward added optional provider arguments and observe byte transactions specifically; preserve its assertions and counts while later stages add their own transactions.
