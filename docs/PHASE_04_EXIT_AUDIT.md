### 4. Scanner authority, admission and read/log effects

The [browser scanner routes](../routes/web.php) remain session/CSRF scanner routes. [API routes](../routes/api.php) currently provide token login/profile/logout only. [ScannerController](../app/Http/Controllers/ScannerController.php) contains `dashboard`, `index`, `ticket`, `recentScans`, `manualSearch`, `validateQr`, `verify`, `manualAdmit` and `admit`; `scannerEvent`, `findQrCode`, `applyAdmissionToLockedGuest` and `recordScan` are relevant helpers. GET `ticket`/`verify-token` aliases render the authenticated scanner page; they are not future public guest-ticket routes. Exact scanner role, active-account entry refresh, HTTPS/throttles, offline locks and bounded admission transactions exist. Manual admission locks an Event-scoped Guest; QR admission locks QR/Guest and checks Event equality. Counter and history writes conserve capacity. However, controller/middleware assignment resolution can use cached relationships and selected/default fallbacks; they do not form one fail-closed current assignment/active-Event boundary. Global token lookup hydrates Guest/Event before the ordinary equality check. Validation/verification also write Checkin/ScanLog and cannot be classified as harmless reads. This is existing [R04](RISK_REGISTER.md), not a new exploit claim.

**Phase 4 source proof needed:** one authority contract across all scanner paths and middleware: explicit canonical persisted assignment, allowed current Event state, exact Guest/QR lineage and no selected/default fallback. Assignment must not imply customer management rights. Characterize response/log differences; retain counters, history and offline exclusions. Online lost-response idempotency remains R07/shared admission work rather than an authorization-task addition.

**Actual-environment proof:** selected assignment/revocation schedules, intended-host load/locks and real HTTPS/camera/device behavior. Retain [P3-010 synthetic MySQL admission evidence](MYSQL_ADMISSION_REHEARSAL.md): selected last-entry pairs and interrupted-counter rollback already passed. It is not configured-owner, hosted-throughput or Android interoperability proof. Shared unification belongs to P5/P13; versioned APIs/devices remain P14/P15.

## Finite exit decision

1. Give each of the four runtime families one complete endpoint/helper contract and acceptance decision. Retain existing guards and their explicit limits. A new task needs a demonstrated supported-boundary gap or new intended caller; do not automatically extend trusted callbacks into further receipt/after-write tasks.
2. Prove legacy owned/foreign/unsafe context refusals at actual row/payload/byte boundaries, plus ordinary positives, offline compatibility and token/code/capacity/history conservation. Any supported customer action needs its explicit current membership/resource contract; closed features must remain evidenced as closed.
3. Complete the ordinary-media decision. Protected controller responses alone cannot satisfy file isolation. Name file/SQL partial outcomes and recovery ownership without claiming arbitrary-adapter undo, perfect erasure or unknowable commit certainty.
4. Freeze and preserve the verified source; run meaningful affected regression gates only for implementation. Reuse unchanged selected engine evidence, including [staff](MYSQL_STAFF_REHEARSAL.md), [workspace provisioning](MYSQL_WORKSPACE_PROVISIONING_REHEARSAL.md) and [package generation](MYSQL_PACKAGE_GENERATION_REHEARSAL.md). Add schedules only where changed composition requires them. SQLite builder intent is not real engine locking.
5. After all four family decisions, compare the completed matrix with the original P4 gate. Declare only the precise source-preparation result supported, then consider P5 contract work in sequence. The present audit does not complete Phase 4 or expose customer writers/signup.

Actual rollout remains separately gated by configured schema/count/invariant inventory, legitimate ownership/platform approvals, DB-plus-protected-file/key restore, maintenance/writer fencing and intended-host/security/device evidence. [Migration gates](SAAS_MIGRATION_PLAN.md) and [backup requirements](BACKUP_AND_ROLLBACK.md) control those decisions. Historical connection failures are not a new availability observation; no service startup or real-data action follows from source preparation.
